## Bordes resueltos
- **CA-1 dice 'al enviarse', pero en attempt_submitted todavía no hay nota.** → Se notifica en attempt_graded, que ocurre en la misma petición de envío. Incluye los cierres automáticos por tiempo. Los intentos abandonados no se notifican porque no tienen nota, y las previsualizaciones tampoco.. _Criterio:_ CA-1 exige las notas. El estudiante no percibe diferencia, porque ambos eventos van seguidos. _(Habría preguntado: ¿Los intentos abandonados sin enviar también deben informarse al sistema externo?)_
- **Con preguntas de ensayo no hay nota al enviar: queda pendiente de calificación manual.** → Hay dos avisos. El primero sale al enviar, con attempt_grade null y grade_status 'pending'. El segundo sale cuando la calificación manual deja sumgrades distinto de null, con grade_status 'graded'. Cada uno tiene su propia clave de idempotencia.. _Criterio:_ CA-1 pide notificar al enviar, pero si no hubiera un segundo aviso el sistema externo nunca recibiría la nota. Es reversible: quitar uno de los dos avisos es un cambio de una sola línea en el observer. _(Habría preguntado: ¿El sistema externo prefiere recibir dos avisos o solo uno cuando la nota esté completa?)_
- **Una nota puede cambiar después de informada: el profesor corrige el ensayo o se recalifica el examen de forma masiva.** → La corrección manual de una pregunta se notifica de nuevo si cambia sumgrades; misma nota, misma clave, sin envío nuevo. La recalificación masiva (attempt_regraded) NO se notifica en esta versión.. _Criterio:_ El spec habla del envío del intento. La recalificación masiva podría generar muchos envíos y no está pedida. _(Habría preguntado: ¿Las recalificaciones masivas deben llegar al sistema externo?)_
- **Contrato del sistema externo: campos, respuestas e idempotencia.** → Se hace POST JSON a la URL configurada, con idempotency_key, student, quiz, attempt, timestamp, attempt_grade, final_grade, max_grade y grade_status. Los nombres se confirman con las sondas; si la respuesta real contradice este plan, manda la respuesta real. La clave es estable entre reintentos (intento + sumgrades, o 'pendiente') y también va en la cabecera Idempotency-Key.. _Criterio:_ La restricción del spec es no asumir el contrato. Si un reintento sigue a un timeout en el que el receptor sí guardó el dato, no debe duplicarse. _(Habría preguntado: ¿El contrato de la demo es el definitivo o el sistema real tendrá otro formato?)_
- **Qué cuenta como envío exitoso: un 200 puede traer un error en el cuerpo y un proxy puede responder HTML.** → Éxito solo con HTTP 2xx, cuerpo JSON válido y status == 'accepted' (duplicate true también es éxito). Se guarda el id externo. Cualquier otra respuesta es fallo y se registra con el código HTTP y el cuerpo crudo.. _Criterio:_ El spec exige sobrevivir a que el sistema 'responda distinto a lo esperado'. Mirar solo el código HTTP daría por entregado un resultado no guardado. _(Habría preguntado: ¿El sistema real siempre devuelve status 'accepted' al aceptar?)_
- **Qué fallos se reintentan, cuántas veces y qué pasa al agotarse.** → Se reintenta todo fallo, incluidos 4xx, con el backoff nativo y el tope de 12 ejecuciones (unas 34 h). Al fallar la última ejecución, el envío queda en estado 'agotado' con la última causa. El destino se lee en cada ejecución, así que corregir la URL sirve para los envíos que siguen en cola.. _Criterio:_ CA-3 dice que un fallo se reintenta, sin excepciones. Un 404 o 422 puede deberse a una configuración mala que el administrador corrige. El límite evita reintentos infinitos. _(Habría preguntado: ¿Hay un plazo máximo aceptable para que el resultado llegue? ¿Alguien debe recibir un aviso al agotarse?)_
- **Reenvío de envíos agotados.** → No hay botón de reenvío. El envío agotado queda en el registro con sus datos y su causa.. _Criterio:_ No está en el spec. Se evita ampliar el alcance y queda visible en el registro. _(Habría preguntado: ¿Producto necesita reenvío manual para los agotados?)_
- **Límite de tiempo de cada llamada HTTP.** → 5 s para conectar y 10 s en total por llamada, como constantes de la tarea. La llamada se hace en cron, nunca en la petición del estudiante.. _Criterio:_ Un destino colgado no debe retener al cron. El modo 'timeout' del receptor no responde nunca. _(Habría preguntado: ¿El sistema real puede tardar más de 10 s en responder?)_
- **Destino sin configurar, o bloqueado por la seguridad de cURL de Moodle.** → Sin URL no se hace HTTP y queda una fila en estado 'omitido' con la causa 'destino no configurado', sin reintento. Si Moodle bloquea la URL, es un fallo normal: se reintenta y se registra el mensaje real de Moodle. No se usa ignoresecurity.. _Criterio:_ CA-4 pide que cada resultado sea inspeccionable. Saltarse curlsecurity abriría un riesgo de SSRF. Para la demo la URL es http://receptor/resultados, porque localhost:8091 solo existe desde el host. _(Habría preguntado: ¿Los intentos anteriores a configurar el destino deben enviarse después?)_
- **Autenticación contra el sistema externo.** → Sin autenticación ni token en esta versión. El único ajuste de destino es la URL.. _Criterio:_ CA-2 solo pide el destino y el contrato conocido no exige autenticación. Agregar un secreto sin saber su esquema sería inventar contrato. _(Habría preguntado: ¿El sistema real exigirá autenticación? ¿De qué tipo?)_
- **Datos personales que salen de Moodle e identificación del estudiante.** → student lleva id, username e idnumber; no se envían ni nombre ni correo. quiz lleva id, cmid y nombre. Se declara el envío externo y las tablas en la Privacy API, con exportación y borrado.. _Criterio:_ CA-1 pide identificar al estudiante, sin más detalle. Se envía lo mínimo. Los datos del entorno son sintéticos. _(Habría preguntado: ¿Con qué identificador reconoce al estudiante el sistema institucional?)_
- **Alcance: si la notificación aplica a todos los exámenes o solo a algunos.** → Aplica a todos los exámenes del sitio cuando hay destino configurado. No hay opción por examen.. _Criterio:_ El spec habla de un único destino configurado por el administrador y no menciona opciones por examen. _(Habría preguntado: ¿Hay exámenes que no deban informarse?)_
- **Quién ve el registro, qué guarda y cuánto se conserva.** → Página de administración protegida por la capacidad local/resultadoext:viewlog (manager y admin). Hay una fila por envío y otra por cada llamada: fecha, URL, código HTTP, errno y error de cURL, y cuerpo crudo hasta 2000 caracteres, siempre escapado al mostrarlo. No hay purga automática.. _Criterio:_ CA-4 exige la causa real. El cuerpo viene de un tercero: sin escapar sería un XSS en una página de administrador. El tope evita guardar respuestas enormes. _(Habría preguntado: ¿Hay una política de retención para este registro? ¿Los profesores deben verlo?)_
- **Las sondas no cubren todos los modos de fallo. La fábrica ejecuta 8 como máximo y corta cada una a los 15 s.** → Las sondas verifican el contrato, el duplicado, el 200 con error y el HTML de proxy. http500 y timeout no se sondean: se fuerzan de verdad en las pruebas E2E. /_control y /_reset son herramientas de prueba, no contrato, y el plugin no depende de ellas.. _Criterio:_ Se priorizan las respuestas más engañosas. El tratamiento genérico de 'no éxito' cubre los otros dos casos. _(Habría preguntado: ¿Se conocen otros modos de fallo del sistema real?)_
